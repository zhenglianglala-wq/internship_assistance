## 1. 阶段① 前端：两个采集入口

入口一「来源管理」（SourceManager 弹窗）：管理多个来源，点「开始采集」批量跑所有启用的来源，`POST /api/collection/runs` 不带 sourceId。

入口二「快速采集」面板（BossChrome.tsx，发现机会页顶部）：针对 BOSS 单来源，表单预填你的偏好（关键词、城市、翻页批数 maxPages、详情上限 detailLimit、仅实习开关）。它的「自动采集 BOSS」按钮逻辑：若 BOSS Chrome 来源已存在则 `PATCH /api/collection/sources/:id` 更新配置，不存在则 `POST /api/collection/sources` 创建，然后 `POST /api/collection/runs {sourceId}` 只跑这一个来源。

拿到 **202 Accepted**（不是 200——REST 语义：任务已受理，但还没完成）。之后前端靠轮询刷新：App.tsx 里有一个 useEffect，只要 `data.collection.activeRun` 非空，就每 1.5 秒重新 `GET /api/bootstrap`。所以采集期间你关掉面板、甚至刷新页面都不影响任务——任务活在服务端。

## 2. 阶段② 请求穿过中间件（index.mjs 开头的 app.use）

每个请求依次过五道检查，任何一道不过直接返回 403/400 JSON：

1. **Host 白名单**：hostname 只允许 localhost / 127.0.0.1 / [::1]——服务虽然只绑 127.0.0.1，这道是双保险（防 DNS rebinding 类攻击）。
2. **安全响应头**：nosniff、no-referrer、X-Frame-Options: DENY、完整 CSP（script/font/connect 限 self、style 允许 inline、img 允许 data:、frame-src 允许 blob: 的 PDF 预览）；/api 路径再加 Cache-Control: no-store。
3. **Origin 白名单**：带 Origin 头的请求必须来自 4318 或 5173（dev 端口）。
4. **本地令牌**：所有非 GET 的 /api 请求必须带 `X-Local-Token`，值是服务启动时随机生成的 32 字节 hex，只在 `/api/bootstrap` 响应里发给前端。作用：其他程序/网页就算知道端口，也写不了你的数据。
5. **workspace 路由**：`X-Workspace: demo|personal` 决定 `req.db` 挂哪个库。示例空间的拦截不在这里做，而是每个路由内部的 `real(req)` 函数——demo 直接抛「请切换到我的空间」。

## 3. 阶段③ startCollection：互斥、落库、异步启动（collection.mjs）

三个关键动作，顺序很重要：

```js
if(running.has(s)) throw 409 '已有采集任务正在运行'        // 1. 互斥
const run = s.put('collectionRuns', {...status:'running'...}) // 2. 先落库
running.set(s, run.id)
setImmediate(()=>void performCollection(s,run,sources))    // 3. 再异步执行
```

- **互斥用的 key 是 store 对象本身**（`running.has(s)`），天然按 workspace 隔离——示例空间和个人空间可以各跑各的（虽然 demo 会被路由层拦掉）。
- **run 记录先落库再执行**：这是「刷新页面任务不丢」的原理。服务若在执行中重启，`initCollection()` 会扫描所有 status 还是 running 但内存里没有对应任务的 run，标记为 `interrupted`，提示「已保存的岗位保留」。
- **setImmediate** 保证 HTTP 202 响应先返回，采集在事件循环的下一轮才开始。
- 来源筛选：手动触发跑所有 `enabled` 的来源（或 sourceId 指定的一个）；定时触发额外排除 `boss_safari`（Safari 需要人工看着当前页面）。注意 **boss_chrome 不被定时排除**——面板上写明「定时采集需浏览器已打开且登录有效」，浏览器没开时采集会以友好错误结束，不影响其他来源。

## 4. 阶段④ performCollection 主循环

逐来源执行，**每个来源独立 try/catch**：一个来源挂了只在自己的 result 里记 error，其他来源照常。这就是「部分完成 partial」状态的来源。

错误信息有一层「翻译」：底层网络错误（ENOTFOUND/EAI_AGAIN → 域名解析失败、TimeoutError → 连接超时、fetch failed → 网络或代理问题）被转成用户能懂的中文提示。

**BOSS Chrome 的统计修正**是个精妙细节：因为采集过程中每个批次就实时入库了（见 6.5 的「阶段保存」），最后再整体 saveSourceResult 时所有岗位都会算成 unchanged。所以 performCollection 在采集**前**先快照所有岗位的 contentHash（baseline），采集**后**用「差值」重算 added/updated/unchanged——added = 不在 baseline 里的 id，updated = hash 变了的。

> **举例理解统计修正**：采集前库里有 100 个岗位。本次采集读了 3 批共 110 个岗位，其中 10 个全新、2 个薪资描述变了。因为每批都实时入库，最后整体 saveSourceResult 逐个对比时，库里早已是这 110 个的最新版本——返回「新增 0、更新 0、110 未变化」，用户真正关心的任务级贡献（新增 10、更新 2）在这次返回里丢失了。修正做法：采集前拍 baseline 快照（岗位 id → contentHash 对照表），采集后自己对比——采到的 id 不在 baseline 里 → 新增（本次运行期间首次出现）；在 baseline 里但 hash 变了 → 更新；其余 → unchanged。于是前端拿到真实的「新增 10 · 更新 2」。这段代码外面有 `if(source.kind==='boss_chrome')` 包着——只有 Chrome 通道需要修正，因为它逐批实时入库；其他来源读完后一次性入库，直接统计就是准的。设计意图一句话：**数据安全用阶段保存（中断不丢），统计准确用差值重算（对比任务前后快照）**。。

收尾 finally：写 finishedAt、清 running、若定时开启则推进 `nextRunAt`。

## 5. 阶段⑤ collectSource 分发器与 resolveSource

> **先看这一节在解决什么问题**：不同公司把岗位数据放在完全不同的地方——腾讯在自己官网的接口里；很多外企把招聘页托管在 Greenhouse/Lever/Ashby 这类招聘平台上（一个平台挂几千家公司，平台提供公开 JSON 接口）；有的官网页面里埋着 JSON-LD 标准格式的岗位数据（为 Google 收录按标准标注、藏在网页源码 script 标签里的结构化数据）；BOSS 需要浏览器登录态。你在界面上只做一件事——粘贴网址点采集；程序却要先搞清楚「这个网址属于哪一类、该用哪套方法读」。本节就是这两步：**resolveSource 负责安检与分类，collectSource 负责按类分发到专用读取器**。类比快递集散中心：先分拣（看地址判断走哪条线），再交给对应片区的配送员，最后所有包裹走统一入库口（normalizeJob → saveSourceResult）。表中「完整性判定 complete」是全节最关键概念：只有把来源**读全了**，才有资格断言「这次没出现的岗位=下架」；只读到一部分就不能下结论，否则会误杀还在招的岗位（它是第 8 节下架语义的前提）。
>
> **总览：八种来源各用什么方式拿数据（三档）**
>
> | 档位 | 来源 | 方式 |
> |---|---|---|
> | 一：程序直接发 HTTP（公开数据，无需浏览器） | Greenhouse / Ashby / Lever | 程序自己请求平台的**公开 JSON 接口**，拿现成 JSON 解析 |
> | 一 | 腾讯官网 | 程序请求官网公开查询接口（返回 JSON），抓前先查 robots |
> | 一 | 普通官网 website | 程序下载网页 **HTML 源码**，解析其中的 JSON-LD 结构化数据 |
> | 二：指挥真实浏览器，从浏览器手里拿数据（需登录态/有反爬） | BOSS · Chrome（主力） | 专用 Chrome 访问搜索页；**列表=截获浏览器自己发出的 joblist.json 响应**；详情=在页面内执行 fetch（带登录态）；DOM 解析仅作状态巡检兜底 |
> | 二 | BOSS · Safari（旧） | 在已登录 Safari 当前页执行 DOM 解析读卡片，点击补详情——**唯一纯解析 DOM 的通道** |
> | 三：不访问网站 | 手机导入 | 用户粘贴分享文字/上传截图（Mac Vision OCR），核对后直接入库——用户提交的快照 |
>
> 为什么 BOSS 不能像 Greenhouse 那样直接发请求？它的接口需要**登录 Cookie**、URL 带反爬签名参数（伪造不出）、还有风控（code 37 专抓伪造请求）。所以只能让真浏览器带真实登录态去访问，程序不碰 Cookie，只站在旁边「抄」浏览器的响应——「截获」这个词只属于 BOSS Chrome：浏览器发的请求，程序在旁抄内容。

**resolveSource** 是入口守门员，做四件事：

1. `publicUrl()` 校验 URL（见第 12 节 SSRF 防护）；
2. **平台黑名单**：实习僧整体拒绝（「此平台目前不支持自动采集」）；zhipin.com 只放行 `/web/geek/jobs` 搜索页路径；
3. **kind 推断**：按 hostname 猜来源类型（zhipin→boss_safari、careers.tencent.com→tencent、boards/job-boards.greenhouse.io→greenhouse、jobs(.eu).lever.co→lever、jobs.ashbyhq.com→ashby、其他→website）；用户显式指定的 kind 与推断不一致就 400，**唯一例外**：boss_chrome 和 boss_safari 共用 zhipin.com 域名，互相放行；
4. **board 提取**：greenhouse/lever/ashby 从 URL 路径取公司标识并校验格式（`^[a-zA-Z0-9_-]{1,100}$`），tencent 校验 attrId 参数只能是 ''/1/2/3（3=实习）。

然后按 kind 分发，五种 HTTP 来源的采集策略：

| kind | 数据源 | 分页 | 完整性判定 |
|---|---|---|---|
| greenhouse | boards-api 官方 JSON | 单次全量 | jobs 数 === 返回数 → complete |
| ashby | posting-api | 单次全量 | 恒 complete（仅保留 isListed===true） |
| lever | v0/postings API | 每页 100，最多 10 页（1000 封顶），页间隔 500ms | 末页不足 100 → complete |
| tencent | careers.tencent.com Query 接口 | 每页 100，最多 10 页，间隔 600ms，Set 去重 | jobs ≥ Data.Count 或末页不满 → complete；且此来源必须先过 robots |
| website | 网页里的 JSON-LD | 列表页 + 同域 ItemList 详情页最多 10 个（间隔 600ms） | 恒 complete:false |

website 来源有个聪明的「跳板」逻辑：如果页面本身没有 JobPosting，但发现了指向 greenhouse/lever/ashby 的链接（`integrations`），自动改用对应平台的采集器重新采集。部分详情页读取失败只记 warning（「部分详情页暂时未能读取」），不整体失败。

**robots 检查**（`allowed()` 函数）：拉取 origin 的 /robots.txt（512KB 上限），内容像 HTML 就当没有 robots 文件，解析结果缓存 1 小时，用 `robots-parser` 库以 UA 'InternshipStudio' 判定 isAllowed。robots.txt 本身 401/403/429/5xx 时**宁可不做**（「暂时无法确认采集规则」）——这是「拿不准就不碰」的设计。

**boss_safari**（旧方案）：osascript 执行 AppleScript，在用户已登录的 Safari 当前标签页里跑 DOM 解析函数读列表，再点击卡片补最多 10 个详情。仅手动触发。

**mobile 通道不走 collectSource**：手机分享在核对表单提交时由 `commitMobile()`（mobile.mjs）直接构造 job 并调用 saveSourceResult 入库——它没有「采集」动作，是用户提交的快照。

## 6. 深潜：BOSS Chrome 采集（本章重点）

### 6.1 三个设计决策（面试最爱问）

1. **为什么要专用 Chrome，而不是直接发 HTTP 请求爬接口？** BOSS 的接口需要登录态 Cookie + 复杂签名参数，硬伪造会被风控拦（错误码 37「环境异常」）。方案：让**真实浏览器**带着真实登录态去访问，程序只负责「导航 + 读结果」。专用（独立 `user-data-dir`）而不是用你日常的 Chrome，是为了隔离：不碰你的个人配置，也避免和你的手动浏览互相干扰。
2. **为什么程序绝不碰 Cookie？** 边界设计：应用只「指挥浏览器做事」，从不导出凭据。登录是你亲手在这个专用窗口里完成的。
3. **为什么截获 API 响应而不是解析 DOM？** 列表页 DOM 是 Vue（前端框架，与 React 同类；BOSS 页面靠它在浏览器里做客户端渲染——服务器返回的原始 HTML 几乎是空壳，岗位卡片是 JS 拿到数据后现场"画"出来的，详见 side-questions.md Q20）渲染的、结构易变、薪资还有特殊字体反爬；而浏览器自己请求的 `/wapi/zpgeek/search/joblist.json` 是结构化 JSON，字段全（明文薪资、每周天数、学历要求）。截获响应 = 拿到浏览器「亲眼看到」的数据。DOM 解析只保留作兜底（guard 巡检时判断页面状态）。

### 6.2 ensureChrome：专用浏览器的生命周期（chrome-cdp.mjs）

启动一个浏览器的完整链路：

1. **找可执行文件**（chromeExecutable）：优先 `BOSS_CHROME_PATH` 环境变量 → 系统 Chrome → Edge → Playwright 装的 Chromium（复用测试浏览器，不重复下载）。
2. **分配调试端口**：`allocatePort()` 用「listen(0) 绑定随机端口再立刻释放」的方式拿一个确定空闲的端口——**不用 Chrome 的 `--remote-debugging-port=0`**，因为那样真实端口只能从文件里事后猜，有被其他进程抢注的风险。
3. **启动**：`--remote-debugging-address=127.0.0.1 --remote-debugging-port=N --user-data-dir=.data/boss-chrome` + 一个本机 marker URL 当首屏页，detached + unref（浏览器独立于服务进程存活）。
4. **等就绪**：最多 15 秒轮询，读 `DevToolsActivePort` 文件 + 请求 `/json/version`，验证 WebSocket 地址确实是 `ws://127.0.0.1:该端口/devtools/browser/xxx`（防端口被抢占后连到陌生浏览器），通过后把 `{port, wsPath}` 存进 `cdp-endpoint.json`（0600 权限）供下次直连。
5. **并发防护**：模块级 `opening` Promise——多个请求同时发现浏览器没开时，只有第一个真正启动，其余等待复用。

### 6.3 connectCDP：一个 40 行的 CDP 客户端

CDP 就是 Chrome DevTools 协议（F12 开发者工具的底层）：WebSocket（一种「持久双向通道」协议——HTTP 一问一答每轮结束，WebSocket 握手一次后保持连接、双方随时主动发消息；短信 vs 打电话。Chrome 靠它主动推送「请求完成了」这类事件，详见 side-questions.md Q12）上跑 JSON 消息，请求带自增 id，响应靠 id 匹配，另外还有事件推送。`connectCDP()` 返回 `{send, on, close}`：send 带超时（默认 12s）和 pending Map 匹配；on 订阅事件；连接断开时 reject 所有挂起请求并给出「请重新打开浏览器」提示。这个手写客户端比引入 puppeteer 依赖轻得多——项目只需要 5 个 CDP 命令。

### 6.4 bossTarget：找到 BOSS 标签页

`Target.getTargets` 列出所有页面，按 binding 文件（boss-target.json）记住的 targetId + URL 必须是 zhipin.com 域 来找目标标签页；找不到且是手动触发就新建一个（Target.createTarget）。每次拿的是**页面级** WebSocket 连接（`/devtools/page/{id}`），而不是浏览器级的。

### 6.5 collectChromeBoss 主流程（boss-chrome.mjs，时序）

> **故事版导读（先读这段，再看下面的时序）**：整个流程 = 程序站在浏览器旁边，盯着它、指挥它、从它手里抄数据。分五幕——
> **第一幕·占坑体检装哨兵**：occupied 锁防止两个任务同时指挥一个标签页；guard 巡检查「还在 BOSS 页吗/登录着吗/有验证码吗/条件被改吗/点停止了吗」；然后挂三个监听器（哨兵）只盯一种响应——BOSS 的岗位列表接口，下载完成就取出内容解码解析，下载失败记错误。为什么靠「监听」而不是程序自己发请求？请求必须由浏览器自己发（带登录态和签名），程序只配在旁边抄。
> **第二幕·出发等待**：命令浏览器导航到搜索页（关键词+城市+1902 只看实习）；程序每 300ms 看一眼数据到了没，最长等 18 秒，期间每 1.5 秒 guard 一次。
> **第三幕·抄一批翻一页循环**：验货（code 0 正常/37 风控）→ 字段翻译成统一格式 → 清洗生成 ID → 仅实习再筛 → 按岗位 ID 存集合；然后注入 JS 翻页（点「下一页」→ 滚动容器 → 滚整页）；保险丝：连续 2 批无新岗位就停（防死循环）、每批歇 2.5s（拟人防风控）；**每抄完一批立刻入库一次（阶段保存）——中途被验证码打断，已抄的批已经在库里**。
> **第四幕·补详情**：列表只有概要，对前 detailLimit 个岗位让页面 JS 自己 fetch 详情接口（带登录 Cookie），先验明正身（详情的岗位 ID/名称必须与列表对上）才合并，状态从「仅列表」升级「有完整详情」。
> **第五幕·汇总**：complete 恒为 false——只读了 3 批不是全量，没资格说「没出现的都下架了」，永不触发下架（对比 Greenhouse 一次拿全量才敢标）。
> **记忆版**：占坑 → 体检 → 装哨兵 → 让浏览器去搜 → 盯着抄、抄一批存一批 → 翻页继续 → 挑几个补详情 → 汇总（不敢说读全了）。程序全程没碰 Cookie，只是在页面里「替你点了几下、滚了几下」。

```text

  → guard() 巡检：页面状态/登录/验证码/搜索条件变更/停止请求
  → Network.enable（缓冲上限 2.5MB/5MB）
```

## 7. 阶段⑥ normalizeJob：所有来源汇成一种形状（job-parsers.mjs)

不管来自哪个通道，岗位都要过 `normalizeJob`：

- **清洗**：cleanText（cheerio 去 HTML、二次实体反转义、压空白）、cleanUrl（仅 http/https、去凭据、去 hash、去 utm_*/ref 追踪参数）。
- **生成 ID**：`sha256(规范化后的 URL)`——这是去重的基石。URL 规范化保证了 `job_detail/abc.html?lid=x` 和不带参数的同一岗位算同一条。mobile 来源没有 URL，用 `公司+岗位+城市` 哈希。
- **推断实习要求**（inferRequirements，纯正则）：从标题+描述里抽 `employment`（实习/全职/兼职/合同）、`workplace`（远程/混合/现场）、`daysPerWeek`（每周 N 天）、`durationMonths`（N 个月）。**抽不出来就保持 null/unknown，绝不编造**——这是全项目的数据原则。
- **employment 判定有优先级**：来源显式标注 > 标题特征 > 描述语义。描述语义那条有个防误判注释：「全职 JD 里提到实习福利 ≠ 实习岗位」——全职特征（N 年以上经验等）优先于实习词命中。

## 8. 阶段⑦ saveSourceResult：去重与生命周期（★ 全章最核心的语义设计）

在一个 SQLite 事务里做两件事：

**第一件：逐岗位 upsert。** 对每个岗位算 `contentHash`——**排除** id/sourceId/sourceName/provider/externalId/browserEvidence 这些「元字段」，只哈希业务内容（标题、描述、薪资…）。这意味着：换个来源名字重采不算更新，描述真变了才算 updated。三种结局：不存在→added；hash 变了或 availability 变了→updated；否则 unchanged。同时维护 `firstSeenAt / lastSeenAt / updatedAt / change` 时间戳。

**第二件：下架扫描（仅当本次快照 complete:true）。** 遍历库里所有「曾由此来源列出」的岗位，本次没出现的，把该来源的 sourcePresence 标记为 listed:false。然后重算 availability：

- 任一来源仍在列 → open（多来源共见：腾讯和 BOSS 都有的岗位，腾讯下架不算下架）；
- 所有来源都不再列出 → missing（下架）；
- expiresAt 已过 → expired（截止）。

> **举例理解 sourcePresence（每个岗位的「目击者签到表」）**：岗位 A 先被腾讯采到（sourcePresence: 腾讯=listed），三天后 BOSS Chrome 也采到同一条（两条都 listed）。6月10日腾讯全量采集，名单里没有 A → 腾讯签到改 listed:false，但 BOSS 还在列 → A 仍是 open，界面一切正常；6月15日 BOSS 全量采集也没有 A → 全部 false → A 变 missing，卡片出现灰色「来源未列出」标签。为什么这么谨慎？「这次没看到」有很多无辜解释（来源临时故障、翻页截断、搜索条件不同），所以下架必须等 complete 全量快照、必须所有来源都不再列出，且**只改采集岗位池的标签、绝不碰申请记录**——「来源不再列出」≠「你的简历被拒」。

三条保守规则值得背下来：**只有完整快照才能触发下架**（部分采集/失败采集绝不）；**失败来源不影响已有状态**；**下架只改 discoveredJobs.availability，绝不联动 applications**——「来源不再列出」和「我的简历被拒」是两回事，语义上严格隔离。

还有一个 BOSS 特有的合并规则：如果库里已存在 detailStatus='detail' 的旧详情，而本次只采到 'list' 级别，**保留旧详情**（描述、天数、时长、详情读取时间都不回退）。

## 9. 阶段⑧ 回到前端：评分与呈现

`collectionSnapshot()`（每次轮询 /api/bootstrap 和 GET /api/collection 都会执行）把 discoveredJobs 全部取出，逐个跑 `matchJob(job, preferences)` 打分：

- 方向：8 个方向各有中英别名表，子串匹配标题+部门+描述；
- 城市：别名表（北京/beijing…）+ 「其他海外」走一个大正则；
- 关键词：全部词都要出现（AND）；
- 出勤/时长：岗位要求 ≤ 你的可用上限才匹配；未标注的字段进 `unknown` 列表，你勾了「保留未标注」就放行并打标；
- `score = 命中理由数×10 − 未标注数`，排序按 score 降序 → lastSeenAt 降序。

卡片上的标签都能对应到数据字段：「详情待补充」= detailStatus==='list'、「内容有更新」= change==='updated'、「来源未列出」= availability==='missing'、「已过期」= expired。详情侧栏展示 browserEvidence 证据（哪个浏览器、何时读取、来源岗位 ID、原文链接）——「每个数据都能回答它从哪来」。

详情侧栏还有两个新功能：**打招呼语生成**（POST `/api/collection/jobs/:id/greeting`：把岗位+简历正文发给模型，提示词约束「≤140 字第一人称、禁止问候语和客套套话、不编造简历外经历」）和**删除岗位**（已收藏成申请的会 409，防止误删有跟踪记录的岗位）。

## 10. 收藏并跟踪：POST /api/collection/jobs/:id/save

幂等设计（同一操作执行多次与一次效果相同，防双击/重试产生重复申请；电梯按钮 vs 电灯开关的类比见 side-questions.md Q21）：先按 `discoveredJobId` 或 URL 查已有申请，找到就直接返回旧的（HTTP 200），不重复创建。新建时：颜色由岗位 ID 哈希决定（稳定不闪变）、stage=已发现、status=saved（对应「已收藏未投递」）、第一条 event 的 **evidence 字段记录完整来源证据**（浏览器/读取时间/岗位 ID/原文链接，mobile 来源则记设备与原始分享文本）。从这里开始，岗位进入星图，交给申请跟踪体系（那是 03 章的故事）。

## 12. 本链路的安全与合规设计清单

- **SSRF 防护**（public-fetch.mjs）：仅 HTTPS、禁凭据/非标端口、禁 localhost/.local/.internal 等主机名、IP 必须公网 unicast 段、DNS 解析的**所有**地址逐一校验、连接固定到已验证的地址（防 DNS rebinding）、手动跟随跳转且每跳重新校验（≤5 次）、响应大小上限、连接超时。
- robots 尊重：拿不准就不采。
- 浏览器边界：专用 profile、只绑 127.0.0.1、只对 zhipin.com 域操作、不导出 Cookie、启动参数白名单式固定。
- 速率拟人：页间隔 500-2500ms、批次上限、详情上限。
- 行为边界：只读不写——不发消息、不投递、不改账号；验证码永远留给用户手动处理。
- 证据留存：每条岗位带 browserEvidence / mobileOriginal，可追溯到「何时从哪里读的」。

## 13. 面试问答预演（先自己答，再看要点）

1. **「你的爬虫怎么应对反爬？」** → 要点：不用裸 HTTP 伪造，用真实浏览器登录态；截获 API 响应而非解析 DOM；拟人节奏与批次上限；code 37/验证码/频率限制的分层识别与安全停止；错误永不丢数据。
2. **「怎么设计去重？」** → 要点：规范化 URL（去追踪参数/hash）→ sha256 为主键 → contentHash（排除元字段）判内容变更 → sourcePresence 多来源共见 → 只有 complete 快照才判下架。
3. **「为什么任务在后台跑还不怕刷新页面？」** → 要点：run 先持久化再 setImmediate 异步执行；前端只轮询状态；重启用 initCollection 把孤儿 running 标记 interrupted；阶段保存保证部分结果落库。
4. **「CDP 是什么，你怎么用的？」** → 要点：Chrome DevTools 协议，WebSocket JSON 消息（id 匹配请求 + 事件订阅）；本项目手写 40 行客户端，只用 Page/Network/Target/Runtime 四个域；专用 user-data-dir + 随机端口 + 端点校验。
5. **「如何防止 SSRF？」** → 要点：五层校验（协议/主机名/IP 段/DNS 全地址/连接固定）+ 手动跳转逐跳复检 + 大小与超时上限。
6. **「并发采集会怎样？」** → 要点：进程内 Map 互斥（409）；工作空间隔离；Chrome 模块独立 occupied 锁；也坦承 Map 是单机方案，多实例需外置（引出企业化演进）。
7. **「AI 在这条链路里干什么？」** → 要点：只有打招呼语生成一处，提示词强约束（字数/人称/禁编造），基于简历事实生成，输出仍需人工核对。
8. **「如果让你改进这条链路？」** → 要点：进程内状态外置（Redis/DB）、采集任务队列化、把 inspector 的 DOM 兜底升级为结构探针、来源失败自动退避重试、企业化时把「实时截获」改为可回放的响应录制。

## 14. 术语速查

- **CDP**（Chrome DevTools Protocol）：浏览器调试协议，F12 的底层；WebSocket + JSON，本项目用它导航页面、截获网络响应、注入 JS。
- **robots.txt**：网站声明的抓取规则文件；robots-parser 库判定某 UA 可否访问某 URL。
- **SSRF**（Server-Side Request Forgery）：诱导服务端去请求内网地址的攻击；本项目是「用户给 URL、服务器去请求」的典型场景，所以防护做在 public-fetch。
- **JSON-LD / JobPosting**：嵌在网页 `<script type="application/ld+json">` 里的结构化数据标准，Google 简历格式的岗位规范。
- **contentHash**：本项目自造词——排除元字段后对岗位业务内容做的 sha256，用于区分「内容变了」和「只是又读了一遍」。
- **幂等**：同一操作执行多次与一次效果相同；save 接口靠查重实现。
- **阶段保存**：本项目自造词——采集进行中每批次即时入库，保证中断不丢已读数据。
