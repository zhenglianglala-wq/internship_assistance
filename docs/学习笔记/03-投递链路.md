## 0. 全景图

```text
（申请详情页：选一份简历 → 「生成投递草稿」）
   │
   │ ① POST /api/drafts {applicationId, resumeId}     生成模板草稿（revision=1）
   │ ② PATCH /api/drafts/:id                          编辑保存（每存一次 revision+1）
   ▼
「待确认投递」页 DraftEditor
   │ ③ 「预览并确认发送」→ POST /api/drafts/:id/prepare {accountId}
   │      返回 5 分钟一次性令牌 + 完整预览（发件人/收件人/主题/正文/附件名）
   ▼
ConfirmSend 弹窗（逐项核对，勾选「我已检查」才可发送）
   │ ④ POST /api/drafts/:id/send {token, approved:true}
   ▼
send 路由五重校验 → status='sending' 先落库 → nodemailer 发送
   ├─ 成功：事务{ 草稿=sent+messageId；申请.events.push(已投递，evidence=messageId) }
   └─ 失败/超时：草稿=unknown，502，永不自动重发

（回声链路）IMAP 同步收件箱 → classify 规则猜阶段 → matchApplication 关联申请
   → 你逐封「确认」→ 事务写入申请进度 → 星图推进
```

一句话记住设计哲学：**邮件是不可逆的对外副作用，所以「不确认不发、不重复发、结果不明就说不明」**。

## 1. 阶段①② 创建与编辑草稿

申请详情侧栏选好简历版本点「生成投递草稿」→ `POST /api/drafts`。后端做的事：校验 applicationId/resumeId 真实存在 → 复制公司与岗位名 → 收件人默认取申请的 contactEmail → 主题模板 `实习申请｜{岗位}` → **正文模板里埋三个「待补充」占位符**（到岗时间/每周出勤/实习时长）→ revision=1 落库。

编辑走 `PATCH /api/drafts/:id`：只有 `status==='draft'` 才允许改（发送后/待核实的草稿只读）；**每次保存 revision+1**——这个数字是后面整个协议的锚点。前端还有一道 dirty 检查：改了没保存，预览按钮会先逼你保存（「预览什么就发什么」的前提）。

「待补充」占位符和 prepare 是联动的：正文里还有占位符，prepare 直接 400「请先补充草稿中的到岗时间、出勤和实习时长」——防止半成品邮件发出去。

## 2. 阶段③ prepare：一次性确认令牌

`POST /api/drafts/:id/prepare {accountId}` 的校验链：demo 空间拒绝（realOnly）→ 草稿必须还是 draft → 收件人必须是合法邮箱 → 无「待补充」残留 → 发件账号真实存在。全部通过后：

```js
const token = randomBytes(32).toString('hex');           // 256位随机
confirmations.set(token, { draftId, accountId, revision, workspace, expires: Date.now()+5*60*1000 });
```

返回给前端的是 `{token, from, to, subject, body, attachment}`——**token 既是预览回执又是唯一的发送凭证**。三个设计点：

- **放内存 Map，不入库**：5 分钟短命 + 一次性，服务重启丢了 = 确认被取消，丢失方向是安全的。这也顺带回答了企业化问题——多实例部署时它才是需要挪进 Redis 的那类状态。
- **5 分钟有效期**：给你足够时间核对，又压短了令牌被滥用的时间窗。
- **revision 快照**：令牌记录的是预览那一刻的 revision，这是第 3 节校验的依据。

## 3. 阶段④ send：五重校验 + 先转移状态再碰网络

`POST /api/drafts/:id/send {token, approved:true}`，校验按顺序：

1. 令牌存在（`confirmations.get` 后**立即 delete**——一次性，重复点击/并发二次确认全部无效）；
2. 未过期（5 分钟内）；
3. workspace 匹配（示例空间的令牌不能在个人空间用）；
4. draftId 匹配（这个令牌只对这一封草稿有效）；
5. **草稿未被改动**：重新读取草稿，`status==='draft' && revision===令牌里的revision`——预览之后你又编辑并保存了草稿？revision 变了，409「草稿已变化，请重新预览」。

五关全过才进入发送，而发送前还有最关键的一步：

```js
// Transition before network I/O; no automatic retry after an ambiguous SMTP result.
d.status='sending'; req.db.put('drafts', d);
```

**在任何网络操作之前，先把状态改成 sending 落库。** 这样如果进程在发送中途崩溃，重启后草稿停在 sending——一眼看出「结果不明」，绝不会被误认为「还没发过」而重发。

然后 `mailServices.transport()` 建 SMTP 连接、`sendMail()` 发送：附件优先用**简历原件文件**（读磁盘字节，保真排版），没有原件的文本简历退化为 Markdown 正文附件。服务器返回的 accepted 列表为空也视为失败。

结果分岔：

- **成功**：在**一个事务**里同时做三件事——草稿置 sent + sentAt + messageId；申请 events 追加「已投递」（source 标注「SMTP 服务器已接受」，evidence 存 messageId）；申请阶段若还在「已发现/已联系」则推进为「已投递」。事务保证「邮件记录」和「申请进度」同生共死。
- **失败/超时**：草稿置 **unknown**，返回 502「发送结果待核实。请先检查发件箱或联系收件人，系统不会自动重发。」finally 里关闭 SMTP 连接。

## 4. 为什么 unknown 而不是「失败」（本章最值得讲的权衡）

SMTP 超时时，邮件**可能实际已经发出去了**（服务器收到了，只是响应没回来）。此时：标 failed → 用户手动重发 → **重复投递**，比发慢了糟糕得多；标 sent → 说谎，可能根本没发出去。诚实的选择只有 unknown（待核实）——把核实权交还给人，系统绝不自动重试。这个状态名的每一个字母都在表达「我不确定」。

顺带是状态机全景：

| 状态 | 含义 | 谁能改它 |
|---|---|---|
| draft | 待编辑待确认 | PATCH 可编辑（revision+1）；prepare/send 只接受它 |
| sending | 网络发送中 | 只有 send 路由能进入；进入后 PATCH 拒绝 |
| sent | SMTP 已接受 | 成功事务进入；附带 messageId 作证据 |
| unknown | 结果不明 | 失败分支进入；唯一出路是人工去发件箱核实 |

## 5. 申请删除的护栏（2026-11 新增，围绕这条链路的保护）

`DELETE /api/applications/:id`：还有 draft/sending 状态草稿的申请直接 409（先把投递列表清干净）；已经有过投递/面试记录的申请，必须显式勾选「同时删除投递记录」才允许删——**删除历史投递痕迹是危险操作，要求二次确认**。真正的删除在事务里连草稿一起清。同理 `DELETE /api/resumes/:id` 被任何草稿引用就 409「为保留投递记录暂不能删除」——证据链不可断。

## 6. 回声链路：收件箱、凭据与消息识别（mail.mjs + index.mjs）

### 6.1 邮箱账号与凭据加密

五种预设 provider（qq/163/gmail/outlook/school，存 IMAP/SMTP 主机端口默认值）。密码型账号（qq/163/gmail 应用密码/学校）存 `secret = encrypt({password})`；OAuth 型（gmail OAuth/outlook）存 `{accessToken, refreshToken, expiresAt}`。

`encrypt/decrypt` 是**本机 AES-256-GCM**：密钥是启动时生成的 32 字节随机 `vault.key`（0600 权限，`flag:'wx'` 保证绝不覆盖已存在的密钥）；密文格式 `iv.authTag.ciphertext` 三段 base64——GCM 自带认证标签，密文被篡改过解密会直接失败。前端 bootstrap 拿到的账号列表**永远剥掉 secret 字段**——凭据不出后端。

`accountAuth()` 每次建连接前检查 OAuth 令牌：到期前 60 秒缓冲即自动用 refreshToken 刷新，并把新密文回写数据库。连接参数一律 TLS（993/465 或 STARTTLS），nodemailer 侧 `disableFileAccess/disableUrlAccess` 防附件路径注入。

### 6.2 /api/sync 同步（竞态修复已落地的那个）

`syncing` Set 按 workspace 防并发 → 逐账号 IMAP 连接 INBOX → 取最近 50 封（单封 512KB 上限）→ **去重**：`sha256(accountId + UIDVALIDITY + UID)` 做消息 id，已存在直接跳过 → `simpleParser` 纯文本化（skipHtml——邮件 HTML 和远程图片一概不加载，这也是 XSS 防御的一部分）→ `classify()` 猜阶段、`matchApplication()` 猜关联 → 存 messages 表 → **写回账号状态前重读数据库**（`const fresh=req.db.get('accounts',account.id); if(fresh){...}`——账号复活竞态的修复现场）。

### 6.3 classify：规则链与优先级

七条正则按优先级排序，命中即返回：**未通过 → Offer → HR 面 → 二面 → 一面 → 笔试 → 初筛**。为什么负向放最前？因为「很遗憾您未能通过本轮一面」同时包含"未通过"和"一面"，顺序错了会识别成一面。输出叫 `proposedStage`（建议阶段）——名字里就写明这只是猜测。

### 6.4 matchApplication：三级匹配，宁缺毋滥

① 申请的联系邮箱 === 发件人（且唯一命中）→ ② 正文含公司名（且唯一）→ ③ 公司名+岗位名都含（且唯一）→ 否则 **null（不猜）**。识别结果必须经人工在收件箱里「确认」：`/api/messages/:id/review` 在一个事务里同时写申请进度（events 追加，evidence 存**邮件原文**——每个阶段推进都有原文证据）和标记消息已处理；「仅标记已处理」按钮则只标记不推进。**没有任何邮件能自动改变申请进度**。

## 7. 失败与边界情况速查表

| 场景 | 检测点 | 行为 |
|---|---|---|
| demo 空间任何发送/同步/账号操作 | realOnly | 400 引导切空间 |
| 草稿含「待补充」就 prepare | 正则检查 | 400 先补全 |
| 预览后编辑草稿再 send | revision 比对 | 409 重新预览 |
| 令牌过期/重放/跨空间 | 五重校验 | 409 |
| 重复点击发送 | 令牌取后即删 | 第二次 409 |
| SMTP 超时/拒绝 | catch 分支 | unknown + 502，绝不重发 |
| 发送中进程崩溃 | sending 先落库 | 重启可见，人工核实 |
| 删除有未发送草稿的申请 | DELETE 检查 | 409 |
| 删除被草稿引用的简历 | DELETE 检查 | 409 |
| OAuth 令牌过期 | accountAuth 60s 缓冲自动刷新 | 刷新失败抛「授权已过期」 |
| 同步进行中再点同步 | syncing Set | 409 |
| 邮件识别不确定 | matchApplication null | 人工手动关联 |

## 8. 面试问答预演

1. **「为什么投递要两次确认？」** → 对外不可逆副作用；prepare 把「要发什么」显式化，send 校验 revision 保证「发的就是看到的」；令牌一次性防重复点击与并发。
2. **「如何保证绝不重复发送？」** → 四道闸：令牌取后即删、sending 前置落库、revision 绑定、unknown 永不自动重试。
3. **「SMTP 超时怎么办？」** → 讲 unknown 权衡：可能已发出，标 failed 诱发重发=重复投递，标 sent 是说谎，unknown 把核实权交还给人。
4. **「发送中进程崩溃？」** → 状态转移先于网络 I/O，重启后 sending 状态可见，人工核实；不自动重发。
5. **「邮箱密码怎么存？」** → AES-256-GCM + 本机 vault.key（0600、wx 标志防覆盖）、三段式密文、secret 永不出后端、GCM 认证标签防篡改。
6. **「邮件怎么自动识别阶段？误识别怎么办？」** → 规则链带优先级（负向优先防「未通过一面」误判）；proposedStage 仅建议；人工确认才写入，evidence 存邮件原文。
7. **「投递记录和申请进度怎么保证一致？」** → 成功事务三写合一；失败不写申请。
8. **「企业化改造这条链路要动什么？」** → confirmations 外置（Redis/DB）、发送队列化+幂等键、多实例下 unknown 核实流程产品化、发送审计日志。

## 9. 术语速查

- **SMTP**：发信协议（ nodemailer 负责）；服务器"接受"≠ 对方收到/读到，所以证据只能写到 messageId 这一层。
- **IMAP**：收信协议（ImapFlow 负责）；UIDVALIDITY+UID 唯一标识邮箱里的一封信，是去重键。
- **OAuth2 refresh token**：长期凭证，用来换短期 access token；本项目到期前 60s 自动续。
- **TOCTOU**（Time-of-check to time-of-use）：检查与使用之间状态被改掉的竞态；revision 绑定就是防它。
- **状态机**：对象只能沿固定路径在少数状态间转移；本链路 draft→sending→sent/unknown 每步都有守卫。
- **事务**：一组写操作要么全成要么全不成；「邮件记录+申请进度」必须同生共死。
