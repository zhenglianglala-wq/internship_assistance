## 1. 为什么需要"记忆"

工作台现在有两个 AI 功能：简历定向建议（`resume-improve`）和手机分享文字整理（`mobile-structure`）。它们每次被调用时都是"初次见面"：

- 你上周让 AI 分析过"武汉前端实习"的岗位，这次它完全不记得；
- 你简历里写了 React 项目，AI 每次都要你把岗位描述重新贴一遍才知道你擅长什么；
- 你明确说过"不想投外包公司"，AI 没地方存放这句话，下次照样推荐。

一句话总结现状：**AI 每次调用都是失忆状态，所有背景都要靠你临时重复输入。**记忆功能就是给它装一个"笔记本"：把你的长期背景、偏好和历史事件记下来，每次 AI 干活时自动翻笔记本。

## 2. 先搞懂几个概念（小白课堂）

### 2.1 短期记忆 vs 长期记忆

用人类类比最好理解：

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 人类类比 | 你正在和 someone 对话，还记得对方 3 分钟前说的话 | 你记得自己是前端方向、讨厌加班、去年面过腾讯 |
| 存活时间 | 几分钟到半小时，用完就忘 | 几个月甚至永久 |
| 掉电（重启服务）后 | 消失 | 还在（存在硬盘数据库里） |
| 工作台里的例子 | 追问简历建议时的这一轮对话 | "我主投后端"、"不想投外包" |

### 2.2 system prompt（系统提示词）

AI 每次回答前，程序会先发一段"隐藏说明"给它，用户看不到这段话。我们就是在这段话里告诉 AI："这位用户主投后端、会 React、不想投外包"。**记忆功能的本质，就是往这段隐藏说明里自动填入正确的内容。**

### 2.3 TTL（存活时间）

Time To Live 的缩写，就是一个倒计时。倒计时结束，数据自动作废。短期记忆用这个机制保证"用完就忘"。

### 2.4 kind（记录种类）

工作台的数据库是一张"万能表格"（SQLite 单表存储，`server/store.mjs`），所有数据按 `kind` 字段分类存放：`applications` 放申请、`resumes` 放简历……我们只要新增一个 `memories` 种类即可，不需要建新数据库。

## 3. 从论文里借鉴了什么（每条一句话）

| 论文 | 学到什么 | 用在哪 |
|---|---|---|
| A-Mem | 每条记忆是带关键词/标签的结构化卡片；新记忆会"演化"旧记忆 | 记忆的数据结构 + 记忆更新机制 |
| MemVerse | 长期记忆分三层：Core（稳定事实）/ Episodic（事件）/ Semantic（概念）；"检索对了 ≠ 用对了" | 记忆分类 + 注入效果的验证方法 |
| MemoRAG | 常用的核心内容常驻，细节按需取 | 注入策略：核心全带、事件按岗位过滤 |
| MemoBrain | 旧对话不要全量携带，把"有结论的部分"压缩成摘要 | 短期追问会话的省 token 做法 |
| MemAgent | 记忆必须有容量上限，强制取舍 | 每类记忆设条数上限 |
| LongMemEval | 记忆系统的五个验收维度：取得出、跨会话、时序、更新、弃答 | 测试验收清单（见第 9 节） |
| MemoryAgentBench | 选择性遗忘（"不要什么"）也是核心能力 | negative 类记忆 |

**明确不抄的**：KV 压缩、参数化蒸馏、强化学习训练管线（需要训练本地小模型，对单用户应用过重）。我们只搬"组织思想"，不搬"训练管线"。

## 4. 总体设计（一图看懂）

```
【写记忆】                              【用记忆】
你手动添加 ──────┐                     AI 干活前（如生成简历建议）
                 │                     ├─ 1. 从 memories 表读出
AI 从你的投递和 ──┤→ 待确认 → 你点头 →  │     已确认的记忆
  消息中提炼候选 ─┘   (pending)  (confirmed)├─ 2. 核心类全量 + 事件类按岗位过滤
                                          ├─ 3. 拼进 system prompt
记忆退役/删除 ←── 你随时可改可删 ←────────┴─ 4. 发给模型（Langfuse 记下 memoryVersion）

【短期追问】
你在简历建议页追问 → 内存会话（30 分钟倒计时）→ 倒计时归零自动清空
```

关键原则（沿用项目红线）：**AI 提炼的记忆一律先"待确认"，你点头才生效；没有相关记忆时 AI 必须明说，不许编造。**

## 5. 长期记忆设计

### 5.1 记忆分四类（type 字段）

| 类型 | 含义 | 求职场景举例 |
|---|---|---|
| `core` | 稳定的个人事实 | "XX大学计算机硕士，2027 届"、"主方向是前端，兼顾 Node 全栈" |
| `preference` | 偏好与条件 | "期望城市武汉，可接受远程"、"偏好每周 4 天到岗" |
| `episode` | 具体事件 | "2026-11-02 腾讯一面被问倒 React 渲染原理，事后补了并发渲染" |
| `negative` | 排除项（不要什么） | "不投外包公司"、"拒绝 996 岗位" |

`negative` 是 MemoryAgentBench 强调的"选择性遗忘"——记住"不要什么"和记住"要什么"同样重要。

### 5.2 每条记忆的字段（数据结构）

存在 `memories` 种类下，每条长这样（逐字段解释见下表）：

```js
{
  id: '8f3c…',                      // 唯一编号，自动生成
  type: 'core',                     // 四类之一（见 5.1）
  content: '主投武汉的前端实习岗',    // 记忆正文，一句话
  keywords: ['武汉', '前端'],        // 检索用关键词（AI 提炼时自动生成）
  tags: ['方向', '城市'],            // 分类标签
  links: [                          // 这条记忆来自哪里（证据链，沿用现有 events/evidence 模式）
    { kind: 'message', id: 'msg-123' }
  ],
  status: 'pending',                // pending=待确认 / confirmed=生效 / retired=已退役（被新记忆替代或删除）
  source: 'ai',                     // manual=你手写 / ai=AI 提炼 / evolution=演化更新
  supersededBy: null,               // 若被新记忆替代，指向新记忆的 id（保留历史，可回溯）
  createdAt: '2026-…',              // 什么时候记下的（时序推理的依据）
  confirmedAt: null                 // 你什么时候点头的
}
```

**为什么要有 `supersededBy` 而不是直接覆盖？** 时序很重要（LongMemEval 的时序维度）：AI 需要知道"11 月 1 日你主投前端，11 月 10 日改主投后端"，而不是只有一条模糊的"主投后端"。保留链路，既能用最新的，也能回看演变。

### 5.3 记忆从哪来（三个入口）

1. **手动添加**：你在界面上一条一条写。手写的直接 `confirmed`（你自己写的当然算数）。
2. **AI 提炼**：点一下"从最近的投递和消息里提炼"，AI 扫描你最近的 `applications`/`messages`，产出候选记忆，一律 `pending`，等你逐条点头。例如从面试通知邮件里提炼出"腾讯约了 11-20 一面"。
3. **记忆演化**（第二期再做）：当新记忆和旧记忆矛盾（方向从前端改为后端），AI 会提议"旧记忆 → retired，由新记忆替代"，这个提议同样要你确认。

### 5.4 记忆怎么被 AI 使用（注入）

每次调 `generateText`（现有 `server/ai.mjs`），在 system prompt 里追加一段，实际拼出来长这样：

```
【关于用户的长期记忆（来自本人确认，未提及的内容不要编造）】
- 核心：主投武汉的前端实习岗（2026-11 起；此前也考虑过北京，已放弃）
- 核心：熟练 React / TypeScript，有 Node.js 全栈项目
- 偏好：每周 4 天到岗，接受 200-300 元/天
- 回避：不投外包公司
- 近事：2026-11-02 腾讯一面复盘：React 并发渲染是弱项
【记忆结束。与以上冲突的历史信息一律以记忆为准。】
```

两条规则（对应 MemoRAG 与 MemVerse 的结论）：

- **Core / preference / negative 全量注入**——个人应用的记忆总量不过几十条，全部带上也不到 1000 字，成本可忽略。**因此不需要向量数据库**，这是本次设计最贴合现有架构的决定。
- **Episode 按需过滤**——只带和当前岗位相关的近 5 条（按岗位关键词与记忆 keywords/tags 匹配，纯数据库查询即可）。
- **弃答规则写进 prompt**："用户询问记忆中没有的信息时，明确回答'没有记录'，不得编造。"——这同时满足 LongMemEval 的弃答维度和项目的"不编造"红线。

**容量上限**（借鉴 MemAgent）：每类上限 core 20 / preference 20 / negative 20 / episode 100，超出时提示你清理，不自动删。

### 5.5 注入点的取舍

第一期只给**简历定向建议**（`resume-improve`）接入记忆——它是唯一需要"了解你"的功能。`mobile-structure`（提取岗位字段）不需要记忆，保持现状。

## 6. 短期记忆设计（追问会话）

场景：AI 给了简历建议，你想追问"第二点展开讲讲，结合我的 React 项目"。

- 新增端点 `POST /api/resumes/:id/improve/ask`，请求体带 `sessionId`（首次可省略，响应里返回）。
- 服务端用内存 Map 存会话（照抄 `confirmations` 的现成模式）：`{messages:[…], applicationId, expiresAt}`，**TTL 30 分钟**，到期自动清空；重启服务即消失——这正是"短期"的定义。
- 每轮把完整 `messages` 数组发给模型；当历史超过 6 轮，把最早的轮次**压缩成一段摘要**拼在开头（MemoBrain 的 FOLD 思想），避免越问越长。
- 前端在简历建议卡片下方加一个输入框和"追问"按钮。

## 7. API 设计（第二期之前只做长期记忆部分）

| 方法与路径 | 作用 | 说明 |
|---|---|---|
| `GET /api/memories` | 列出全部记忆 | 含 pending，前端渲染"待确认"区 |
| `POST /api/memories` | 手动添加一条 | 手写直接 `confirmed`；body：`{type,content,keywords?,tags?}` |
| `PATCH /api/memories/:id` | 确认 / 修改 / 退役 | body：`{status:'confirmed'|'retired'}` 或改 content/keywords |
| `DELETE /api/memories/:id` | 彻底删除 | 硬删除，不可恢复（界面上二次确认） |
| `POST /api/memories/extract` | AI 从最近数据提炼候选 | 生成若干 `pending` 记忆返回；走 `generateText`，同样接入 Langfuse（trace 名 `memory-extract`） |

约定：

- 所有写操作照例要求 `X-Local-Token`；demo 空间禁用（`realOnly`）。
- 响应形状沿用现有错误中间件：`{error:'中文错误信息'}`。
- 注入记忆后，`generateText` 的调用点给 Langfuse 传 `metadata.memoryVersion`（= 已确认记忆条数 + 最近更新时间哈希），便于对比"有/无记忆"的输出质量——直接回应 MemVerse"检索对了≠用对了"的教训。

## 8. UI 设计

放在**设置与连接页**（Settings），新增"关于我的记忆"卡片：

- **待确认区**（有 pending 时置顶显示）：每条一行，右侧两个按钮"✓ 记住"/"✕ 不要"，可先编辑再确认。
- **已生效区**：按类型分四组展示，每条可编辑、可退役（"这条过时了"）、可删除。
- **入口按钮**："手动添加一条"和"从最近数据提炼"。
- 简历建议卡片下方：追问输入框（第二期）。

不改工作台其他页面；不动现有任何 API 的行为。

## 9. 验收清单（测试就照这个写）

单元测试（`tests/memory.test.mjs`，用可注入的假模型断言 prompt 内容，不依赖真实模型）：

1. 手动添加 → 列表可见、状态 confirmed；
2. AI 提炼 → 产物是 pending，确认后才 confirmed；
3. 注入：给前端岗位生成建议时，system prompt 包含已确认记忆内容、不包含 pending/retired 的内容；
4. 过滤：episode 记忆只在与岗位匹配时注入；
5. 时序：新记忆 confirmed 后，旧的同类记忆被提议退役（演化提案正确）；
6. 弃答：无记忆时 prompt 里有"没有记录"的指令文案；
7. 边界：超出容量上限返回中文错误；retired/删除的记忆不再注入；
8. 追问会话（第二期）：30 分钟 TTL 后会话失效；摘要化后 token 数下降；demo 空间禁止写入。

对照 LongMemEval 五维度的真实场景自测（手动验收，记录进 `docs/validation.md`）：

| 维度 | 场景 | 期望 |
|---|---|---|
| 信息抽取 | 存了"熟练 React"，生成前端岗位建议 | 建议提到 React |
| 跨会话推理 | 重启服务后再生成 | 记忆仍生效（SQLite 持久） |
| 时序推理 | 先存"主投前端"，后存"改主投后端" | 建议以后者为准，且说明"已从前端调整" |
| 知识更新 | 存了"不投外包"，岗位建议 | 不再出现外包公司 |
| 弃答 | 问"我面过字节吗"（没记录） | 明确说"没有记录"，不编造 |

## 11. 安全与隐私边界（不变的红线）

- 记忆只存本机 SQLite，不进 GitHub（`store.mjs` 数据目录已被 `.gitignore` 覆盖）；
- AI 提炼只读你的申请/消息数据，全部在本机完成，不新增任何外部依赖；
- 注入记忆后 prompt 变长，Langfuse 上传内容会包含记忆正文——继续知情使用云版，关掉 LANGFUSE 键即同时关闭上传；
- 未经你确认的 AI 提炼永不生效；退役记忆保留链路可回溯，硬删除不可恢复。

## 12. 词汇表

| 词 | 大白话解释 |
|---|---|
| 记忆注入 | 把记忆内容自动拼进发给 AI 的隐藏说明里 |
| pending / confirmed / retired | 待确认 / 已生效 / 已退役（过时下线但留档） |
| 记忆演化 | 新记忆入库时，AI 检查旧记忆是否被替代并提议更新 |
| TTL | 倒计时寿命，到点自动销毁 |
| SQLite / kind | 工作台的本地数据库 / 数据库里的记录分类标签 |
| 向量检索 | 按语义相似度找内容的高级检索；本设计数据量小，用标签匹配即可，不需要它 |
| 弃答 | 没有相关记忆时明确说"没有记录"，禁止编造 |
